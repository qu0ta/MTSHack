# Что нужно от ML-инженера для подключения общего проекта

Дата: 13 ноября 2026.

## Решение команды и текущее состояние

Для сайта используем твою полную цепочку **поиск → контекст → промпт → LLM** через
`rag_api.generate_answer()`. Собственный эксперимент AI Engineer сохранён отдельно
и в рабочем сервисе не используется. Повторно переписывать ответ второй моделью не будем.

Уже реализовано на стороне AI Engineer:

- FastAPI `POST /api/v1/chat` и схемы, совместимые с текущими моделями Go.
- Вызов твоего синхронного кода через `asyncio.to_thread`.
- Инициализация индекса при старте процесса.
- Передача истории, возврат `answer`, `sources` и времени обработки.
- Подготовка заявки из готовых полей бэкенда по явному подтверждению пользователя.
- Проверки с подменённым HTTP, включая запуск настоящего ML-модуля через FastAPI.

**Реальные API из FastAPI и общий запуск Go → Python → ML ещё не проверены.**
Локально сейчас доступна генерация через OpenRouter; это не подтверждает доступность
эмбеддингов и реранкера, используемых твоей цепочкой.

## 1. Сначала нужен рабочий способ запуска вне платформы рейтинга

Пожалуйста, сообщи:

- Какой API используем для генерации, эмбеддингов и реранкера при запуске сайта?
- Доступен ли API организаторов из нашего приложения вне контейнера проверки?
- Какие точные названия моделей, адреса, ограничения запросов и необходимые зависимости?
- Если вне платформы доступа нет — какой вариант ты можешь предоставить для локального
  запуска и демонстрации? Например, согласованный API либо твой локальный сервис.
  Необходимо явно назвать отличия от конкурсного решения.

Текущий сервис ожидает:

| Переменная | Что нужно указать |
|---|---|
| `LLM_BASE_URL` | Базовый адрес API; текущий ML-код использует его для всех трёх типов запросов |
| `LLM_API_KEY` | Ключ генерации; также используется для остальных вызовов, если отдельных ключей нет |
| `LLM_MODEL` | Точное имя модели генерации |
| `EMB_MODEL` | Точное имя модели эмбеддингов |
| `RERANKER_MODEL` | Точное имя реранкера |
| `EMBEDDER_API_KEY` | Отдельный ключ эмбеддингов, если требуется |
| `RERANKER_API_KEY` | Отдельный ключ реранкера, если требуется |
| `KB_PATH` | Локальный путь к приватной базе — папка документов или ZIP |

Секреты передать отдельно по согласованному закрытому каналу, **не вставлять в этот
документ, Git или скриншоты**. В примере окружения достаточно имён переменных.
Если нужны разные адреса для трёх API, это надо отдельно поддержать в ML-коде:
сейчас отдельные ключи есть, но базовый адрес общий.

## 2. Подтвердить версию и сохранить контракт импорта

Сейчас в `ai/app/ml/` лежит неизменённая пара `solution.py` и `rag_api.py` из версии,
которую мы интегрировали: `fca44fd4743c1cc2f9f6de8397ec732b73ad6a3f`.
Подтверди, что это нужная версия, либо передай совместимую пару файлов и commit SHA.
Важно обновлять оба файла согласованно.

Текущий контракт:

```python
init(kb_path=path_to_knowledge_base)  # один раз на процесс при старте

result = generate_answer(
    query="Текущая реплика клиента",
    history=[
        {"role": "user", "content": "Предыдущая реплика"},
        {"role": "assistant", "content": "Предыдущий ответ"},
    ],
)
```

- Функции синхронные; переписывать их на async для FastAPI не требуется.
- `history` содержит предыдущие реплики в хронологическом порядке, **без текущей**.
- Нужна безопасность двух одновременных вызовов после `init()` и отсутствие общей
  истории между клиентами. Общий индекс использовать можно.
- Для ответа нужны непустой `answer: str` длиной до 10 000 символов и `sources: list[str]`.
  Источники — имена документов; пустой список допустим, например для приветствия.
- Твои `documents` и `timings_ms` можно сохранить. Сейчас HTTP-ответ передаёт только
  `sources` и общее время AI-сервиса; расширение debug-панели согласуем отдельно.

Импорт по умолчанию — `app.ml.rag_api`. После объединения веток можно изменить
`ML_MODULE`, например на `ml.rag_api`, без изменения оркестратора.

## 3. Для сайта поправить поведение с заявкой

В текущем ML-промпте есть инструкция при получении контактов подтвердить, что заявка
передана менеджеру. Для сайта это преждевременно: модель не записывает заявку в БД.

Нужно в режиме сайта:

- Не утверждать «заявка создана/отправлена/передана», если нет подтверждения сохранения.
- Допускать предложение связаться с менеджером, уважать отказ клиента.
- Не считать наличие имени, телефона и компании согласием на отправку заявки.
- Не требовать контакты для обычной консультации.

Готовые контакты AI-сервис получает от бэкенда. При `lead_requested=true` Python
сам готовит объект заявки, а Go сохраняет его и подтверждает результат пользователю.
Реализовывать сохранение, регистрацию или второй сбор контактов в ML не требуется.

**Не нужно менять проверенный конкурсный вариант вслепую.** Можно сделать отдельный
режим промпта для сайта. Способ включения сначала согласуем: такого переключателя
в текущем AI-адаптере пока нет.

## 4. Отличать технический сбой от отсутствия ответа в базе

Сейчас часть ошибок API превращается внутри ML в обычную строку fallback. Тогда
FastAPI видит корректный `answer` и возвращает HTTP 200, хотя модель могла быть недоступна.

Предпочтительный контракт для режима сайта:

- Если в базе нет нужных сведений — нормальный ответ консультанта, без выдуманных фактов.
- Если не сработал API/авторизация/генерация — исключение, которое доходит до адаптера.
  Сейчас исключение из `generate_answer()` преобразуется в HTTP 503.
- Если поиск перешёл на BM25 из-за отказа эмбеддингов/реранкера — это явно фиксируется
  как деградация, а не незаметная замена полной цепочки. Согласовать, можно ли продолжать.
- Не выводить ключи, полные заголовки авторизации и персональные данные в логи ошибок.

Если вместо исключения удобнее вернуть поля `status/error`, сначала согласуем формат
и обновим адаптер: **сейчас он эти поля не интерпретирует**. Конкурсный runner при этом
может отдельно перехватывать ошибки и формировать обязательную строку CSV.

## 5. Согласовать время работы и историю

Сейчас Python ждёт ответ до **55 секунд**, одновременно выполняются не более **двух**
вызовов ML. Инициализация индекса проходит до приёма запросов и в эти 55 секунд не входит.

Нужно проверить реальное время `init`, поиска и генерации, а также общий бюджет повторов
API. В текущей копии ML один HTTP-тайм-аут — 90 секунд; несколько повторов могут заметно
превышать время ожидания сайта. Сам по себе тайм-аут FastAPI поток не останавливает.
Нужен согласованный ограниченный бюджет внутри ML либо другая согласованная настройка
тайм-аутов всей цепочки Python/Go/прокси.

Go сейчас готовит до 50 прошлых сообщений. Важны размер контекста и сохранение последних
уточнений: если требуется обрезка, согласовать стратегию без потери актуального вопроса.
AI-сервис может добавить первой репликой `user` справочные параметры объекта из БД
(регион, отрасль, мощность, потребление). Это данные, не инструкции. Структурированные
ФИО, телефон и компания дополнительно в ML не отправляются; написанное в самой истории
остаётся её частью. Просьба проверить, что такой контекст корректно обрабатывается.

## 6. Совместная проверка перед демонстрацией

С рабочими API прогоняем через FastAPI:

- [ ] Обычный вопрос: ответ по KB, ожидаемые источники, время.
- [ ] Продолжение диалога и исправление параметра, например 500 → 900 кВт.
- [ ] Два независимых чата: сведения одного не попадают в другой.
- [ ] Вопрос без ответа в KB и вопрос вне темы: корректный отказ/уточнение.
- [ ] Недоступность API: отличима от нормального ответа, повторы ограничены.
- [ ] Два одновременных запроса: нет смешивания результатов и ошибок индекса.
- [ ] Контакты в переписке: нет ложного подтверждения отправки заявки.

Сохранение заявки в PostgreSQL проверяем отдельно с бэкендером.
Новая отправка в рейтинг для этой интеграционной проверки не требуется.

## Что прислать в ответ в первую очередь

1. Рабочий способ доступа к трём моделям вне рейтинга или явное подтверждение, что доступа нет.
2. Commit SHA нужной версии и конфигурацию без секретов; изменения зависимостей, если есть.
3. Как включить режим сайта с корректным поведением заявки и технических ошибок.
4. Результаты реального запуска: время старта, ответа и ограничения параллельности.

FastAPI, схемы Go ↔ Python, адаптер и подготовку объекта заявки ведёт AI Engineer.
RAG, модели, промпт консультации и конкурсное решение остаются у ML-инженера.

## Обновление после получения файлов site1

Пара `solution.py` / `rag_api.py` версии `2026-11-13-site1` установлена без изменений,
контрольные суммы совпали. Режим сайта, исключения генерации, история и флаги degraded
подключены к FastAPI. Старые запросы выше сохранены как контекст обсуждения.

Остался конкретный вопрос по инфраструктуре: на текущем локальном ключе OpenRouter
`/embeddings` с `baai/bge-m3` и `/rerank` с `qwen/qwen3-reranker-8b` возвращают HTTP 403.
`/chat/completions` с `openrouter/free` работает. Реальные ответы сайта получены с BM25,
но полный поиск не подтверждён. Нужен доступный API для этих моделей или согласованный
локальный вариант. Логи без ключей: локальный `ai/dist/model_probe.json`.

Дополнительно: в присланном `init()` режим сайта включается после построения индекса,
поэтому его 25/10-секундные тайм-ауты ещё не действуют на стартовую загрузку embeddings.
Внешний бюджет FastAPI ограничивает ожидание, но не завершает синхронный поток.
